# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CliPRx is a backend that ingests cloud billing CSV exports (AWS/Azure/GCP), runs them through an ML + rules pipeline, and returns ranked, LLM-authored "sprint ticket" cost-optimization prescriptions. It is a FastAPI service backed by Supabase (Postgres + Storage + Auth) and Google Gemini. Phase 1 (the pipeline itself), Phase 2 (auth, persistence, the full TRD multi-step flow, PDF export), and Phase 3 (the `frontend/` Next.js app) are all complete — see "Phase 2" and "Phase 3" below.

## Commands

There is no backend test framework or linter configured — pipeline changes are verified by running it end to end. The frontend (`frontend/`) has its own commands (`npm run dev`/`build`) — see "Phase 3" below.

```bash
# One-time setup: installs deps from the root requirements.txt, then runs the pipeline test
python setup.py

# Run the FastAPI server (must run from backend/, since backend/main.py uses bare imports like `from parsers... import`)
cd backend
uvicorn main:app --reload

# Run the pipeline against a hardcoded mock CSV, without the HTTP layer (run from repo root)
python test.py
```

`test.py` is the closest thing to a test suite: it feeds a small mock AWS CSV through every pipeline stage and prints the final Gemini-rendered tickets. When changing any pipeline stage, run it to sanity-check the full chain still produces output.

`GET /health` is a plain liveness check (no pipeline logic). Every error response — deliberate (`HTTPException`) or a framework-level 404/validation error — is normalized to `{error, detail, code}` via handlers registered on `starlette.exceptions.HTTPException` (the base class; FastAPI's own `HTTPException` is a subclass, and Starlette's *internal* routing 404s raise the base class directly, so registering on the subclass alone misses those).

`python data/generator.py` regenerates the sample CSVs in `data/samples/` (mixes ordinary background spend with a few rows engineered to trigger real patterns, so the output is immediately useful for testing). See `README.md` for user-facing setup instructions.

Both `requirements.txt` (root) and `backend/requirements.txt` are plain UTF-8 (regenerated via `pip freeze` after a dependency upgrade — see Supabase note below). They're near-duplicates but not identical (root has `nodeenv`/`pyright`, `backend/requirements.txt` doesn't); keep that in mind if dependencies drift between them. **Gotcha:** the `Write` tool in this environment has been observed writing plain `.txt` files as UTF-16LE (no BOM) even when other file types come out as normal UTF-8 — if you need to regenerate either requirements file, write it via a shell redirect (`pip freeze > requirements.txt`) rather than the `Write` tool, and sanity-check with `file requirements.txt` afterward.

**Import style mismatch:** `backend/main.py` imports its own siblings with bare paths (`from parsers.aws_parser import ...`), which only resolves when the working directory/root is `backend/` (see `backend/pyrightconfig.json`'s `extraPaths: ["."]`). `test.py` instead imports via `from backend.parsers... import ...` from the repo root. Match the import style to whichever entry point you're adding code for.

### Environment variables

Loaded from `backend/.env` (gitignored; see `backend/.env.example`). Required:
- `GEMINI_API_KEY` — used by `backend/services/gemini_service.py` to render sprint tickets. Required or the `/api/v1/test-pipeline` endpoint fails outright (`test.py` also refuses to run without it). Uses the free tier, which rate-limits (HTTP 429) after moderate testing volume in a session — the code already falls back to plain text on any API failure, so a 429 during testing is expected/handled, not a bug.
- `SUPABASE_URL`, `SUPABASE_KEY` — a live project with the Phase 2 schema applied (`profiles`/`uploads`/`reports`/`prescriptions`, `supabase/migrations/20260820204902_create_core_tables.sql`). `SUPABASE_KEY` uses Supabase's newer `sb_publishable_...` key format, not the legacy JWT-style anon key — this requires `supabase-py>=2.15` or so; `supabase==2.3.0` (the version this repo originally pinned) rejects the new format client-side with `SupabaseException("Invalid API key")` before even making a request, because it regex-validates the key as a 3-part JWT. If you ever see that error, it's a library-version problem, not a bad credential. Upgrading `supabase` also required upgrading `websockets` (needs `>=13,<16` for `realtime`'s `websockets.asyncio.client` import), `httpx` (pulled to 0.28 as a transitive dependency), and in turn `fastapi`/`starlette` (old `starlette==0.36.3`'s `TestClient` passes an `app=` kwarg to `httpx.Client` that httpx 0.28 removed). The old `gotrue`/`supafunc` packages are obsolete post-upgrade (replaced by `supabase-auth`/`supabase-functions`) and should stay uninstalled.
- `SUPABASE_SERVICE_ROLE_KEY` — bypasses RLS; needed for any backend write on a user's behalf (writing `reports`/`prescriptions` once the pipeline persists results). Backend-only, never expose to a frontend.
- `ANOMALY_THRESHOLD` — optional, defaults to `0.65` in `main.py`; controls the isolation-forest cutoff for flagging a billing row as anomalous.
- `MAX_UPLOAD_SIZE_MB` — optional, defaults to `50`; oversized uploads get a `413`.
- `ALLOWED_ORIGINS` — optional, comma-separated CORS origins; defaults to `*`.

## Architecture: the DIPPA pipeline

The pipeline itself is one linear sequence of pure functions, each taking the previous stage's output and returning the next — no shared state or class hierarchy to trace. It's invoked from two places: `POST /api/v1/test-pipeline` in `backend/main.py` (the original one-shot convenience endpoint — upload+run+persist in a single call, no essential-services declaration step) and `POST /pipeline/run` in `backend/api/pipeline.py` (the real TRD-documented flow, run after `POST /upload/csv`). Both call the exact same stage functions and the exact same `backend/services/persistence.py` helpers — read either one top to bottom to see the full flow, then dive into individual stage modules.

1. **Data Ingestion** — `backend/parsers/{aws,gcp,azure}_parser.py`. Each `parse_<provider>_csv(bytes) -> pd.DataFrame` normalizes a provider-specific CSV export into the same 8-column schema: `service_name, cost_usd, usage_quantity, usage_type, region, billing_period_start, billing_period_end, tier`. `service_name` is stripped before case-folding/space-replacement (a padded `"  AmazonEC2  "` must not become a different service than `"AmazonEC2"`), and `cost_usd`/`usage_quantity` have commas/`$` stripped before numeric coercion (a comma-formatted `"1,240.50"` must not silently become `0.0`). `tier` is read from a source `tier` column if the CSV has one (digit extracted, defaults to `3` for anything unrecognized), else defaults to `3` (fully mutable) — this is a pragmatic stand-in for the TRD's intended design (tier as a separately-declared, Supabase-backed classification, not a CSV column). Any new provider parser must emit exactly this schema, since every downstream stage assumes it.

2. **Predictive Modeling** — `backend/ml/isolation_forest.py`. Fits an `IsolationForest` (scikit-learn) over `cost_usd`, `usage_quantity`, and a derived `cost_per_unit`, min-max normalizes the anomaly scores to `0.0–1.0` into a new `anomaly_score` column. Datasets under 10 rows skip the model entirely and use a median-multiplier heuristic instead (too few points to fit a meaningful forest).

3. **Pattern Matching** — `backend/ml/pattern_matcher.py`. Filters rows to `anomaly_score >= threshold`, then evaluates each against the provider's JSON pattern library (`backend/patterns/{aws,gcp,azure}_patterns.json`, 30 patterns per provider) using simple `equals`/`contains` trigger conditions on a field. A match produces a raw prescription dict with estimated savings range and engineering-hours range pulled straight from the matched pattern. Patterns also carry `immutable_blockers` (e.g. `["tier1"]`, `["tier1","tier2"]`) consumed later by conflict resolution. **Cross-service guard:** for patterns keyed on `usage_type` (not `service_name`), a match is also checked against `PATTERN_ALLOWED_SERVICES` (AWS) or `SERVICE_CATEGORY_MAP` (Azure) so a coincidental substring match on the wrong service (e.g. an RDS row's usage_type happening to contain "Node:ra3", Redshift's marker) doesn't produce a wrong-service recommendation. AWS needs the precise per-pattern allowlist rather than a broad category because some AWS services are genuinely multi-category in real billing (EBS volume/Elastic IP costs bill under the `AmazonEC2` service line) — adding a new usage_type-keyed AWS pattern means adding its `pattern_id` to the right service set(s) in that map, or it'll be silently rejected for every row.

4. **Risk Assessment** — `backend/ml/failure_scorer.py`. Computes a rule-based infrastructure `risk_level` (`cost_usd > 500` → High; `tier == 2` AND high usage-quantity variance across that service's own line items in this upload → High; `tier == 2` alone → Medium; else Low — `compute_usage_variance_flags()` is the variance proxy, since the ingestion schema has no historical/multi-period data to measure real variance across billing periods) and reconciles it against the pattern's own `downtime_risk`, always taking the *higher* of the two (never downgrade a risky action just because the underlying service is cheap). High risk gets a `failure_cost_estimate` of 4x monthly cost.

5. **Conflict Resolution** — `backend/conflict_resolver.py`. Applies the three-tier safety model: `tier == 1` items are dropped entirely (fully immutable — never surfaced); `tier == 2` items whose pattern blocks `tier2` are flagged `is_conflicted` (core service, action modifies it); items where the action's risk exceeds the service's baseline risk *at any level* (Low→Medium, Medium→High, Low→High — not just the 2-step Low→High jump) are also flagged conflicted. **Note:** the TRD's literal spec (§5.5) only calls for the Low→High 2-step case; flagging every 1-step increase too is a deliberate, requested deviation from the doc, not an oversight. Conflicted items survive in the list but are marked, not removed.

6. **ROI Ranking** — `backend/roi_ranker.py`. `roi_score = (avg(savings_min, savings_max) / avg(hours_min, hours_max)) * risk_multiplier`, where `risk_multiplier` is `1.0/0.7/0.4` for Low/Medium/High. Conflicted items are forced to `roi_score = 0.0` so they sort to the bottom rather than being excluded. Output is sorted descending by ROI (savings as tiebreaker) with `rank_position` injected.

7. **Actionable Insights** — `backend/services/gemini_service.py`. Sends each ranked prescription dict to Gemini (`gemini-3.6-flash`) asking for a Jira-style sprint ticket; on any API failure it falls back to a plain-text `"Execute action: {recommended_action}"` string rather than failing the request.

When adding a new pipeline stage or modifying an existing one, preserve the "list of dicts flowing through, each stage adds/mutates keys" contract — nothing here uses typed models (no Pydantic schemas for the prescription objects), so field names are the only contract between stages.

## Phase 2: Auth + Database (complete)

**Database — done.** `supabase/migrations/20260820204902_create_core_tables.sql` creates `profiles`/`uploads`/`reports`/`prescriptions` per TRD §4, with RLS on every table scoped to `auth.uid()` (`prescriptions` has no `user_id` of its own, so its policy joins through `reports`), a trigger that auto-inserts a `profiles` row on Supabase Auth signup (nothing else populates it), and a nightly `pg_cron` job hard-deleting reports past `expires_at` (TRD §8.3's 30-day retention). Applied and verified live — `npx supabase migration list` shows it recorded on the remote, and all four tables are queryable with RLS correctly returning zero rows for unauthenticated requests. To modify the schema, add a new migration (`npx supabase migration new <name>`) rather than editing this file after the fact; `npx supabase db push` applies pending migrations (add `--dry-run` to preview, `--yes` to skip the confirmation prompt in non-interactive contexts).

**JWT verification — done.** `backend/api/auth.py`'s `get_current_user` FastAPI dependency, wired into `GET /auth/me` in `main.py`. **Deviates from TRD 2.2/7.1 by necessity, not choice:** the TRD describes a static `SUPABASE_JWT_SECRET` for HS256 verification, but this project's Supabase Auth signs tokens with ES256 against a rotating key set published at `<SUPABASE_URL>/auth/v1/.well-known/jwks.json` (confirmed by querying it directly) — there is no usable shared secret to verify against. Verification uses `PyJWKClient` (from `PyJWT`, already a transitive dependency via `supabase-auth`) instead, which needs no secret, just the public JWKS. Verified against a genuinely-issued token (created a pre-confirmed test user via the Admin API using `SUPABASE_SERVICE_ROLE_KEY`, signed in for a real access token, confirmed `/auth/me` correctly extracts `user_id`/`email`, then deleted the test user — Supabase's anonymous sign-in is disabled on this project, and email/password signup requires confirming a real inbox, so the Admin API is the only way to get a valid token without a frontend).

**Persistence — done.** Shared helpers in `backend/services/persistence.py` (`persist_upload`, `create_pending_report`, `finalize_report`, `mark_report_failed`) are used by both `POST /api/v1/test-pipeline` and the split multi-step endpoints below, so they can't drift apart. `persist_upload` stores the raw CSV in the `cliprx-uploads` Storage bucket (path `{user_id}/{upload_id}/{filename}`) and inserts an `uploads` row. Reports use two-phase persistence: `create_pending_report` inserts a `status='running'` row *before* the pipeline runs, then `finalize_report` computes `total_savings_min/max` from non-conflicted prescriptions and `conflict_count` from all of them, updates the row to `status='complete'`, and inserts one `prescriptions` row per item — including conflicted ones (`is_conflicted`/`conflict_reason`/`roi_score: 0` is the point of keeping them). If the pipeline throws mid-run, `mark_report_failed` sets `status='failed'` instead of leaving the row stuck at `running` (best-effort — swallows its own errors so it never masks the real exception). All writes use `get_supabase_admin_client()` (service role, bypasses RLS) since the backend writes on the already-authenticated user's behalf, not as their own Supabase session. Known accepted gap: if the process is killed mid-request, a report can still get stuck at `running` forever — fixing that needs a timeout/heartbeat mechanism, which is genuinely out of scope (would need real background-job infrastructure, which doesn't exist anywhere in this codebase).

**The full TRD multi-step flow — done.** `backend/api/{upload,pipeline,reports}.py` implement all six endpoints: `POST /upload/csv` and `GET /upload/{id}/services` (returns a `ServiceRow` list — `service_name`, `total_cost_usd`, `line_item_count`, `default_tier` — aggregated per service via `services/csv_ingest.py::build_service_rows`; `default_tier` takes the *minimum* tier across a service's line items, biasing the UI's pre-filled default toward "assume protected" rather than "assume safe to touch"), `POST /pipeline/run` and `GET /pipeline/{id}/status`, and `GET /reports` (list) / `GET /reports/{id}` (detail) / `DELETE /reports/{id}` (soft-delete, sets `deleted_at`). `services/ownership.py`'s `get_owned_upload`/`get_owned_report` are the shared "does this row actually belong to this user" check every endpoint calls first — required because the admin client bypasses RLS, so ownership has to be enforced in application code; always 404 on a mismatch, never 403, so a request can't distinguish "doesn't exist" from "exists but isn't yours."

**How `/pipeline/run` gets the parsed data back without re-uploading:** `services/csv_ingest.py::fetch_upload_dataframe` re-downloads the CSV from `cliprx-uploads` Storage using the stored `uploads.file_path`/`uploads.cloud_provider`, then re-parses it — the parsers are pure functions of the bytes, so this deterministically reproduces the same DataFrame `/upload/csv` originally produced. No cache/session layer exists or is needed. The `essential_services` array in the request body (`{service_name, tier, notes}`, `tier` a Pydantic `Literal[1,2,3]` for free 422 validation) overrides the parser's default tier per service — `df["tier"] = df["service_name"].map(overrides).fillna(df["tier"]).astype(int)` — services not mentioned keep whatever tier the parser already assigned (itself the CSV-column stopgap or `3`). `service_name` values must match exactly (the same normalized form `ServiceRow` returned); no fuzzy matching.

**Deliberately synchronous, not truly async:** the TRD's `status: pending/running/complete/failed` implies `/pipeline/run` might return before completion, polled via `/pipeline/{id}/status` — but there's no background job system anywhere in this codebase (no Celery/RQ/task queue), and the pipeline runs in a few seconds. `/pipeline/run` does the work in-process and only returns after `finalize_report`/`mark_report_failed` has already run; `status` goes straight from `running` to `complete`/`failed`, skipping an observable `pending`. `estimated_seconds` in the response is the actual measured wall-clock duration, not a real estimate.

Verified end-to-end against the live project with two real throwaway users (43 assertions, all passing): upload → re-derive services list → cross-user 404 → run with tier overrides → confirm the tier-1 service's prescriptions are fully dropped and the tier-2 service's prescription is present but `is_conflicted`/`roi_score: 0` → list/detail/status all correctly scoped by owner → soft-delete → confirm the row survives with `deleted_at` set and prescriptions untouched → cross-user delete rejected → invalid-tier request rejected with 422 → legacy `/api/v1/test-pipeline` still works unchanged → both test users deleted, cascade confirmed.

**PDF export — done.** `backend/services/pdf_service.py::generate_report_pdf(report, prescriptions, cloud_provider)` renders a branded PDF via ReportLab's `platypus` layout (title, a summary table of total savings/prescription count/conflict count, one section per prescription with risk-color-coded text and a conflict callout where applicable, and a "Generated by CliPRx" footer with page numbers — matching PRD 6.8). Wired into `GET /reports/{report_id}/pdf` in `backend/api/reports.py`: **generated once and cached**, not regenerated on every download — a report is immutable after `finalize_report()` runs, so on first request the PDF is built, uploaded to the `cliprx-reports` bucket at `{user_id}/{report_id}.pdf`, and `reports.pdf_path` is set; subsequent requests just re-download that same stored file (falls through and regenerates if the cached file is somehow missing/corrupt despite `pdf_path` being set). Returned as `Response(media_type="application/pdf", headers={"Content-Disposition": 'attachment; filename="cliprx-report-{id}.pdf"'})`, matching TRD 3.4's "PDF binary stream with Content-Disposition: attachment." Verified end-to-end against the live project (11 assertions): correct headers/content-type, real PDF content (`%PDF` header, real byte count), first and second downloads byte-identical (proves the cache path is actually being hit, not silently regenerating), `pdf_path` correctly set in the DB, and cross-user access rejected with 404 same as every other report endpoint.

**Not done:** nothing — Phase 3 (below) closes the last gap.

## Phase 3: Frontend (complete)

`frontend/` is a Next.js 16 (App Router) + TypeScript app, built from a Claude-Design canvas export (two `.dc.html` artboards + a design-token system, supplied outside the repo) rebuilt as real code — the source files aren't checked in, only the resulting app. Plain CSS throughout (no Tailwind): the design tokens (`_ds/.../tokens/*.css`) were copied verbatim into `frontend/styles/tokens/` and layered with hand-written classes in `frontend/styles/{landing,app-dashboard,auth}.css`, matching the source design's own hand-written-inline-styles approach rather than translating to a utility framework.

**Commands** (run from `frontend/`):
```bash
npm install
npm run dev     # http://localhost:3000, needs .env.local (see .env.local.example)
npm run build   # also used by Vercel; requires the same env vars at build time
                 # since NEXT_PUBLIC_* values are inlined into the client bundle
```

**Routes:** `/` (marketing landing page, static), `/login` + `/signup` (Supabase email/password auth — built new, since the source design explicitly never designed auth screens; signup shows a "check your email" state matching the backend's confirmed-email requirement), `/app` (the dashboard — a single client component cycling through 5 screens: upload → declare tiers → run pipeline → reports list → report detail, backed by real state instead of the source design's hardcoded mock data). `/app` redirects to `/login` when there's no Supabase session (`lib/useSession.ts`).

**Backend wiring:** `frontend/lib/api.ts` is a typed fetch wrapper, one function per backend endpoint, attaching `Authorization: Bearer <token>` from the current Supabase session (`frontend/lib/supabase.ts`) and reading `NEXT_PUBLIC_API_BASE_URL` for the backend origin. Field names are matched exactly to what the backend actually returns (verified live, not guessed) — see the Phase 2 endpoints above. One deliberate simplification: `GET /reports`/`GET /reports/{id}` don't carry `cloud_provider` (it only lives on the `uploads` row), and re-deriving it per report would mean an extra `GET /upload/{id}/services` call per row (which re-downloads and re-parses the CSV) — so the reports list/detail screens omit the provider badge the source design showed, rather than adding that load.

**Deployment:** see `docs/DEPLOYMENT.md` — Render (free tier) for the backend, Vercel (free `*.vercel.app` domain) for the frontend.

### Adding a new cloud provider

1. Add `backend/parsers/<provider>_parser.py` exporting `parse_<provider>_csv(bytes) -> pd.DataFrame` that emits the standard 8-column schema described above.
2. Add `backend/patterns/<provider>_patterns.json` following the existing pattern schema (`trigger_condition`, `recommended_action`, `savings_range_min_pct`/`max_pct`, `engineering_hours_min`/`max`, `downtime_risk`, `complexity`, `immutable_blockers`).
3. Wire the new branch into the `provider` dispatch in `backend/main.py`.
